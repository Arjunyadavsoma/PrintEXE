## 1. Authentication

The real SaaS backend authenticates devices with standard bearer auth — **not** a
custom `X-PrintShop-Device-Token` header (zero grep hits for that header in the SaaS repo).

| Header | Purpose | Logged? |
| --- | --- | --- |
| `Authorization: Bearer <deviceToken>` | Long-lived device token (73-char, two UUIDs joined by `-`) | **No** (token is the secret) |
| `X-PrintShop-Companion-Version` | Companion semver (advisory; logged, not enforced; `426 Upgrade Required` gate planned at v1.0.0) | Yes |

All authenticated endpoints return `401` if the token is missing, malformed, or revoked.
The backend hashes the token with `HMAC-SHA256('print-agent-salt', token)` and looks up
the `PrintAgent` row by `tokenHash`. On success, **every** authenticated call refreshes
the agent's `isOnline=true, lastSeenAt=NOW()` — so heartbeat/poll/status/sync all double
as heartbeats.

**Token format:** `crypto.randomUUID() + '-' + crypto.randomUUID()` → 73-char ASCII.
Local validation regex: `/^[0-9a-f-]{73}$/`. **Long-lived, no TTL, no expiry** — until
revoked via `DELETE /agents/{agentId}` (owner JWT, web only).

## 2. Pairing

> **⚠ Conflict with the brief (§4).** The brief specifies a short-lived **pairing
> ticket** flow: the website creates a ticket, presents a `printshop://pair?...` link,
> the companion opens it, and the companion **exchanges the ticket** with the backend.
> The real SaaS backend implements **paste-token** instead: the shopkeeper copy-pastes
> a long-lived device token generated by `POST /agents/register` (owner JWT, web only).
> There is no `/pair` endpoint, no ticket TTL, no atomic consume step.
>
> This is a **change request for Agent 1** (SaaS owner), not companion work. The
> companion does NOT invent a ticket flow. See `docs/CONTRACT_COMPATIBILITY.md` §3 conflict #1.

### Actual pairing flow (paste-token)

1. Shopkeeper signs into the website (owner JWT via `POST /api/v1/auth/login`).
2. Shopkeeper opens Printer Setup → "Register new agent".
3. The **web dashboard** (not PrintEXE) calls `POST /api/v1/agents/register` with
   `Authorization: Bearer <ownerJWT>` and body `{name, os?, version?, printerName?}`.
4. The server generates `token = uuid() + '-' + uuid()`, hashes it, inserts a
   `PrintAgent` row (only the hash is stored), and returns the plaintext token
   **exactly once**: `{agentId, deviceToken, shopId, shopName, warning}`.
5. The web dashboard shows the token in a modal; the shopkeeper copy-pastes it into
   PrintEXE's pairing field.
6. PrintEXE validates `/^[0-9a-f-]{73}$/`, DPAPI-encrypts it
   (`DataProtectionScope.CurrentUser`) at `%LocalAppData%\PrintShop\Companion\Security\device.dat`,
   then sends `POST /agents/heartbeat` once. `200` = valid token; `401` = wrong paste / revoked.

**The `printshopcompanion://pair` URI scheme exists in the companion + installer but the
backend has no URI handler and no ticket endpoint.** The companion's
`MagicLinkPairingService` is a vestige that forwards a URL `token` to the paste-token
path; the live pairing entry point is the Login view's paste field.

### Pairing recovery states the companion handles

- Invalid token format (regex mismatch) → "That doesn't look like a PrintShop device token."
- Backend unavailable → "Can't reach the PrintShop server. Check your internet and retry."
- 401 on heartbeat → "This token has been revoked or is wrong. Get a new one from the website."
- Existing device already paired → preserve the existing credential; do NOT silently overwrite.

## 3. Heartbeat

```
POST /api/v1/agents/heartbeat
Authorization: Bearer <deviceToken>
Content-Type: application/json

{ "printerName": "<windows default printer>", "version": "0.6.0", "os": "Microsoft Windows NT 10.0.22631.0" }
```

All fields optional; `{}` is valid (missing fields retain prior agent-row values).

→ `200 OK` envelope `{success:true, data:{agentId, online:true, ts:"<ISO8601>"}}`.

- Default interval: **60 s** (per `PRINTEXE_DEVICE_LIFECYCLE.md`). The online threshold
  is **30 s**: a device is "online" iff `lastSeenAt` is within 30 s.
- `tokenStillValid` is NOT in the response. Revocation is detected via `401` on the
  next authenticated call or the `agent.revoked` Socket.IO event (§4).
- **The companion's heartbeat is currently NOT driven by a timer** — see
  `docs/AUDIT.md` §16 item #7. Every authenticated REST call refreshes `lastSeenAt`
  server-side, so steady-state polling at 2 s keeps presence fresh on its own, but an
  explicit heartbeat timer is the documented contract.

## 4. Job delivery

### 4.1 Socket.IO (production realtime)

- **URL:** `wss://printshop-saas-three.vercel.app/?XTransformPort=3003` — the
  `?XTransformPort=3003` query is **required** (without it Caddy routes to the Next.js
  app on port 3000 which doesn't serve Socket.IO → HTTP 400).
- **Path:** `/`. **Transport:** WebSocket (polling fallback allowed).
- **Reconnect:** `Reconnection=true`, `ReconnectionAttempts=∞`, `ReconnectionDelay=2000ms`.

**Client→server (companion emits):** exactly one — `auth` with `{token: <jwt>}`. The
server verifies the HS256 JWT (sub=`agent:<agentId>`, shopId, role=`staff`, type=`access`,
TTL=900s), rejects if invalid, then `socket.join('shop:<shopId>')` and emits `auth-ok`.

**Server→client events the companion listens for** (the full catalogue; see
`docs/CONTRACT_COMPATIBILITY.md` §2.5):

| Event | Payload | Companion action |
| --- | --- | --- |
| `auth-ok` | `{shopId, role}` | mark connected |
| `auth-error` | `{message}` | refresh JWT via `POST /agents/token`; re-emit `auth`; if refresh 401 → treat as revoked |
| `job.dispatch` | `PrintJobDto + deliveryAttemptId` | persist to SQLite queue (idempotent on `jobId`); **no wire-level ACK** — claim is via REST `POST /agents/jobs/{id}/status {status:"printing"}` |
| `job.printing` | `{jobId, fileId}` | informational (the companion drove this transition) |
| `job.completed` | `{jobId, fileId}` | informational |
| `job.failed` | `{jobId, fileId, error}` | informational |
| `job.needs_review` | `{jobId, fileId}` | surface in UI: the backend's stale-recovery worker (5-min threshold) moved this job to `needs_review` |
| `order.ready` | `{orderId}` | informational |
| `agent.revoked` | `{agentId, agentName, cancelledJobs}` | if `agentId == this device`: clear local credential, stop, show "Revoke this PC" |
| `delivery.received` | `{jobId, agentId, agentName, receivedAt, checksum?}` | informational |
| `sync.pushed` | `{count, deviceId}` | log; do not hammer the backend |

> **Note:** the previous doc's `registerDevice`/`DeliverJob`/`AckJob`/`ReportStatus`
> hub method names were **wrong**. The real backend has only one inbound handler
> (`auth`). The dead `CompanionProtocol.HubMethod*` constants are now `[Obsolete]`.

### 4.2 HTTP poll (fallback)

```
GET /api/v1/agents/jobs/pending
Authorization: Bearer <deviceToken>

→ 200 OK envelope {success:true, data:{jobs: [PrintJobDto, ...], agentId}}
```

Default interval: **2 s** while Socket.IO is down; optional 10-15 s even while up.
There is **no `/jobs/{id}/ack` endpoint** — the companion claims a job by POSTing
`status:"printing"` (which is a conditional UPDATE on the backend).

### 4.3 Reporting final status

```
POST /api/v1/agents/jobs/{jobId}/status
Authorization: Bearer <deviceToken>
Content-Type: application/json

{ "status": "printing" | "completed" | "failed" | "needs_review", "lastError": "<≤500 chars>", "printerName": "<≤200 chars>" }
```

→ `200 OK` envelope: success `{jobId, status, applied:true}` OR skip
`{jobId, skipped:true, reason:"job is '<cur>' — ..."}` (HTTP 200, not an error).

- `status:"printing"` is an **atomic conditional claim**: `UPDATE ... WHERE id AND shopId
  AND status='queued'`. The loser gets `{skipped:true}` and should cancel the job locally.
- `status:"completed"` is conditional on `status='printing'`. Side-effect: if all the
  order's files are `completed`, the order flips to `ready` and `order.ready` is published.
- `status:"failed"` is unconditional; sets `lastError`.

**Accepted: printing | completed | failed | needs_review** (Phase 1: the SaaS accepts needs_review from printing/queued states for uncertain physical outcomes; completed is also accepted from needs_review for operator resolution). `queued`/`assigned` are
server-internal. See `JobStatusMappingTests.cs` for the local→backend mapping.

### 4.4 Reporting receipt (v0.5.x+)

```
POST /api/v1/agents/jobs/{jobId}/received
Authorization: Bearer <deviceToken>
Content-Type: application/json

{ "deliveryAttemptId": "<uuid>", "checksum": "<64 hex chars>", "fileSize": 1234567, "receivedAt": "<ISO8601>" }
```

All fields optional; idempotent (short-circuits if already received). Response:
`{jobId, received:true, cleanupScheduled:true, message}`. This is the gate for cloud
deletion: the server-side cron schedules `FileCleanupTask` at `now + 15 min`.

## 5. PDF download

```
GET {downloadUrl from PrintJobDto}
```

- **No auth header** — the URL is a presigned S3/Supabase URL with a **15-min TTL**.
- Returns `application/pdf`. The companion refuses > 100 MB (`CompanionProtocol.MaxPdfBytes`).
- The companion verifies SHA-256 against the `checksum` from the job **if the backend
  provides one**. (Current bug: `HttpPrintShopBackend.MapToRecord` leaves `PdfSha256`
  null for backend-delivered jobs — see `docs/AUDIT.md` §4. Verification falls back to
  the hash of the downloaded bytes.)

## 6. Sync (v0.5.x+)

- `GET /api/v1/sync/pull?cursor=<ISO8601>&limit=<1-500>` → `{changes: SyncChange[], nextCursor, hasMore}`.
- `POST /api/v1/sync/push` (body `{changes:[{entity, id, action, data, clientRevision, baseRevision}]}`)
  → `{results:[{id, accepted, conflict, serverRevision?, serverData?, reason?}]}`.
  **Only `Customer` is pushable in v1**; other entities return
  `{accepted:false, conflict:false, reason:"<entity> is server-authoritative"}`.
- `GET /api/v1/sync/status` → `{deviceId, shopId, syncCursor, lastSyncAt, lastPushAt, agentName, isOnline}`.

## 7. Errors

Envelope on error: `{success:false, error:{code, message, details?}}`. Codes:
`VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`,
`INTERNAL_ERROR`, `ADAPTER_ERROR`. See `PRINTEXE_ERROR_CODES.md` for the retry policy.

| Status | Meaning | Companion behaviour |
| --- | --- | --- |
| 401 | Device token invalid / revoked | Stop processing; clear credential; surface "Revoke this PC" |
| 404 | Job no longer available | Mark Cancelled in queue |
| 409 / `CONFLICT` | Conditional update lost the race | Re-fetch pending; reconcile (the `{skipped:true}` response) |
| 5xx / `INTERNAL_ERROR` | Transient backend error | Exponential backoff; 5, 15, 45, 135, 405, 600s cap |
| `RATE_LIMITED` | 429 | Back off per `Retry-After` if present |

## 8. Remote commands

> **⚠ Conflict with the brief (§8).** The brief specifies a remote command channel
> (RefreshPrinters, Pause, Resume, Cancel, Retry, TestPrint, Diagnostics,
> CheckForUpdates). The real SaaS backend has **no command channel** of any kind —
> no `CommandType`, no `/agents/{id}/command` endpoint, no server→client command event.
> The only server→client signals are the broadcast events in §4.1 (job dispatch +
> revocation + status notifications).
>
> This is a **change request for Agent 1** (SaaS owner). The companion does NOT invent
> commands. The command handlers are implemented as **local UI actions** (tray menu,
> dashboard buttons) — useful regardless. See `docs/CONTRACT_COMPATIBILITY.md` §3 conflict #2.
