# Sync Architecture — PrintEXE Offline-First Design

## Overview

PrintEXE uses the PrintShop SaaS backend as the single source of truth. The local SQLite database is an **operational cache** — it stores:
1. The print job queue (for the background print engine)
2. Cached orders + analytics (for offline dashboard viewing)
3. A pending-operations queue (for offline order status changes)

The local database is NEVER authoritative for business data. It is a cache + a queue.

## What Can Be Done Offline

| Operation | Offline? | Reason |
| --- | --- | --- |
| View cached orders | ✅ | Local SQLite cache |
| View cached analytics | ✅ | Local SQLite cache |
| View shop profile | ✅ | Local SQLite cache |
| View print queue | ✅ | Local SQLite (already exists) |
| Start order (paid → printing) | ⚠️ Queue | Queue the API call, push when online |
| Complete order (ready → collected) | ⚠️ Queue | Queue the API call, push when online |
| Cancel order | ⚠️ Queue | Queue the API call, push when online |
| Update order notes | ⚠️ Queue | Queue the API call, push when online |
| Download PDF for printing | ❌ | Needs presigned URL from backend |
| Create new order | ❌ | No backend API for this (website creates orders) |
| Login | ❌ | Needs backend authentication |
| Printer discovery | ✅ | Windows API, no backend needed |
| Test print | ✅ | Local printer, no backend needed |

## Pending Operations Queue

```sql
CREATE TABLE pending_ops (
    op_id           TEXT PRIMARY KEY,   -- UUID generated by PrintEXE
    operation_type  TEXT NOT NULL,       -- 'start_order', 'complete_order', 'cancel_order', 'update_notes'
    target_id       TEXT NOT NULL,       -- order ID
    payload         TEXT NOT NULL,       -- JSON body for the API call
    created_at      TEXT NOT NULL,
    attempts        INTEGER DEFAULT 0,
    next_attempt_at TEXT,
    last_error      TEXT,
    status          TEXT DEFAULT 'pending'  -- pending, in_flight, completed, failed
);
```

### Sync Flow

1. **User clicks "Start Order" offline**
   - PrintEXE creates a `pending_ops` row: `{ op_id: UUID, operation_type: 'start_order', target_id: orderId, payload: {} }`
   - The local cache updates the order status to "printing" (optimistic)
   - UI shows "Pending sync" indicator

2. **Connectivity restored**
   - SyncEngine picks up pending ops ordered by `created_at`
   - For each op: `POST /shops/me/orders/{target_id}/start` with the payload
   - On 200: mark op as `completed`, update local cache with server response
   - On 409 (conflict): mark as `failed`, log the conflict, keep local cache as-is
   - On 5xx: increment attempts, set `next_attempt_at` with backoff

3. **Idempotency**
   - The `op_id` UUID is sent as `X-Idempotency-Key` header
   - The backend should deduplicate on this key (not yet implemented — needs backend change)
   - Client-side: if the same order has a pending 'start_order' op, don't create a second one

## Conflict Policy

| Entity | Conflict Policy |
| --- | --- |
| Order status | Server-authoritative. The backend's `transitionStatus` uses conditional WHERE clauses — if the order's status changed on the website between our fetch and our push, the push returns 409. PrintEXE re-fetches and shows the conflict. |
| Order notes | Last-write-wins (notes are non-financial, low-stakes) |
| Print job status | Server-authoritative with atomic claim (conditional UPDATE WHERE status='queued') |
| Financial records | Server-authoritative — PrintEXE never creates financial records, only reports print status |

## What Needs Backend Changes

| Change | Why |
| --- | --- |
| `X-Idempotency-Key` header support on order mutation routes | Prevents duplicate offline ops from being applied twice |
| `GET /shops/me/orders?since={timestamp}` cursor-based incremental sync | Allows PrintEXE to pull only changes since last sync, not full list every time |
| `GET /shops/me/sync-checkpoint` | Returns the server's current timestamp + count of changed records since a given time |

These are additive — they don't break existing website functionality.
